## 4. 为什么这 392 条补不了（以及为什么「从源库补」也不该做）

### 4.1 库内没有任何可指的行

`runArchive` 的语义就是 `DELETE FROM messages WHERE session_id = ?`，然后 `message_count=0` / `cleanup_at=now`（`src/capture/archive.ts:171`）。
msgId 的定义是「**本库** `messages.id`」，行没了，语义上就不存在一个「正确的 msgId」可写。
硬写一个数字进去 = 制造「有 msgId 但查不到」，读端会把它判成「原文已归档」—— 与现在的 `via='none'` 结果一样，但**多了一个假 id**，正是 `capture/rebuild.ts:59` 明令禁止的那种（「宁缺勿假」）。

### 4.2 源库确实还在，392/392 都能对上 —— 但这不能用来回填

把 179 场归档会话拿去 `C:/Users/crx/.zcode/cli/db/db.sqlite` 里核了一遍（只读）：

| 核对项 | 结果 |
|---|---|
| `(source_session_id, sequence=决策 seq)` 在源库命中 | **392 / 392** |
| 源消息 `time_created` == 决策 `at`（毫秒级） | **392 / 392** |
| 源消息 text part 包含决策句首 | **392 / 392**（唯一 1 条「不符」是探针只有 5 字「升级到v2」，按规则判「太短不猜」，不是真不符） |
| 可回灌的成本 | 26,767 条源消息 / 约 **8.2 MB** 正文 |

问题不在「对不对得上」，在**回灌完 msgId 仍然是错的**：

1. 源库的 message id 是 `TEXT`（`msg_xxx`），跟本库 `messages.id`（INTEGER AUTOINCREMENT）**不是同一个命名空间**，不能直接写。
2. 真要补，必须先**把正文灌回本库**（拿到新 id），再**重跑抽取**让 `extractDecisions` 写 `msgId: m.id` —— 两步都超出「回填脚本」的边界，且第二步会**改写 decisions 内容**（v27 规则可能改掉/删掉条目），已经不是「只加一个字段」了。
3. 灌回来的路径现在也是**堵死的**（这是好消息，说明归档没漏水）：
   - 179/179 场的 zcode 游标 `cursor.rowid == MAX(message.rowid)` ⇒ `readNew` 永远不会再吐旧消息；
   - `upsertCapturedSession` 不看 `cleanup_at`，而 `sync` 只在 `read.messages.length > 0` 时才清 `cleanup_at`（`src/capture/sync.ts:372`）—— 两者互锁，归档会话不会自己复活。
4. **归档的设计目的就是删正文**（99.4% 空间回收）。为了让 392 条决策能回跳，把 8.2 MB 正文塞回库里，是把隐私/体积上已经付过的代价再买一次。**不建议，除非有明确的产品需求。**

### 4.3 真正的结论

> **msgId 只能在写入时得到，回填救不回来已归档的部分。**
> v25/v27 已经把写路径修好（存活会话 253/253 = 100%），剩下的缺口是归档策略的**必然结果**，不是 bug。
> 要缩小它，只有两条路：**① 归档前把出处钉死**（见 `5 建议 2）；**② 接受并如实报告**（现状，读端已经会打印「seq 回落 · 该条无 msgId」）。

## 5. 建议

1. **不要在真库上跑 `--apply`。** 今天它就是 0 条；写了也没有一条会变。脚本的价值是**回归防线**（这次实测：现在这条路上 0 条待补，将来若有人把 msgId 写坏、或换库重来，一条命令就能看出有多少条能补）。
2. **把出处钉在归档之前**（唯一能真缩小缺口的改法，需要另开任务）：在 `decisions` 里额外存一个**跨库稳定**的锚 —— 例如 `srcMsgId`（源库 message id 字符串）+ `srcSeq`。它不依赖本库 rowid，因此归档删正文后**仍然可核**（今天 392/392 都能在源库对上，说明这条路可行性 100%）。改动面：`extract.ts` 输出形状 + `version.ts` 递增版本 + 三条读路径的回落顺序。**注意**：那是 `src/` 的改动，不在本任务写区。
3. **不要为这 392 条去改归档策略**（比如「有决策的会话不归档」）：那会立刻让 179 场 / 18,694 条消息重新占据库容，收益（392 条回跳）与代价（8.2 MB + 隐私面扩大）严重不对等。
4. **8 条悬空 msgId 保持原样。** 它们正是 R13「有 msgId 但查不到 ⇒ `via='none'`，**刻意不回落 seq**」那条设计的服务对象；实测读端行为正确（不会拿 seq 去猜、不会指到错的那条）。若哪天这些会话复活，`rebuild` 的 `remapAnchorMsgIds` 会按 seq 重映射或删掉该字段，不需要提前处理。
5. **子代理会话单独看一眼**（98 场 / 152 条）。它们的决策多是子任务局部结论，混进「已确认结论」未必是用户想要的；这是另一个话题，此处只登记数字。
